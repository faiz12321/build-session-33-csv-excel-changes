Before Excel import: flag leading zeros and long digit strings

Short answer

Excel can convert numeric-looking text, including leading zeros and digit strings beyond its 15-digit numeric precision. What happens depends on the import method, version and conversion settings. This small checker flags just two ASCII digit-string patterns. It does not predict every Excel change or prove a CSV is safe.

Common mistakes

  1. Treating a risk flag as a prediction. Excel's version, import method and automatic-conversion settings matter. This tool does not run Excel.
  2. Calling a no-hit file safe. Dates, scientific notation, formulas and other conversions are not checked. A no-hit report only means the two patterns were absent.
  3. Saving over the original after Excel changes it. Keep a separate original and verify the imported values before saving. A later text format cannot recover digits already lost.
  4. Reusing an existing practice folder. Setup refuses sample if it exists. Start in a separate new lesson folder rather than deleting or overwriting existing data.

Frequently asked questions

What exactly does it flag?

After stripping surrounding whitespace, ASCII digit strings longer than one character that start with 0, and ASCII digit strings of 16 or more digits. A value can count in both groups. It does not parse signs, decimal points, exponents, dates, formulas or non-ASCII digits.

Does Excel always change these values?

No. Microsoft documents automatic conversions and ways to preserve text, including import settings and newer automatic-conversion controls. The flags tell you what deserves attention, not what your Excel configuration will do.

Why do long identifiers need care?

Excel numeric values have 15 digits of precision. If a longer identifier is converted to a number, later digits can be lost. Preserve such identifiers as text during import and verify them against the original. This checker does not record Excel itself.

What malformed files are rejected?

The checker reports UTF-8 decoding errors, missing/blank or duplicate header names, inconsistent record field counts and CSV parser errors such as an unclosed quote. Quoted multiline records are supported. These are limited checks, not a promise that all malformed input is detected.

Will the checker or tests change my CSV?

The checker reads the chosen CSV and prints a report. Tests use their own temporary folders and check source bytes, size, modification time and directory contents on a small fixture. The separate sample setup writes a new fictional CSV only when sample does not already exist.
